# Methodrail

Use Methodrail proportionally. Match depth to uncertainty and risk. Ordinary work is inspect, edit, and the cheapest honest check. Load extra skills only when they remove real uncertainty or risk.

Check project context before rediscovering information. If `.methodrail/PROJECT.md` exists, read it before substantive work. Follow its pointers to knowledge, control guidance, and the project verification skill. Prefer those pointers over copying canonical docs into context. Treat stored notes as current only after a freshness check.

Use deterministic tools for deterministic facts. Prefer git, compilers, tests, linters, and package managers over speculation.

Distinguish inference from observation. Reading source is not runtime evidence. Label important claims as inferred, observed, test-confirmed, traced, historically-confirmed, or unknown.

Prefer fresh evidence before completion claims. Do not claim success, a fix, or "done" without verification produced in this turn. If the project already has a verification skill, control documentation, runtime guidance, or a test workflow, reuse it. Do not invent a parallel ceremony.

Escalate rigor only when uncertainty or risk requires it. Simple work must stay simple.

Preserve valuable learning without duplicating discoverable state. Propose durable notes only when rediscovery is expensive. Keep permanent context small.

Use installed Methodrail skills from `.claude/skills/` only when their descriptions match the task.
