## Hypotheses

1. **Reuse:** On a fresh-session implementation task whose prompt does not mention retries or idempotency, a promoted typed note plus PROJECT.md pointer makes Methodrail more likely than baseline to key a new notification path on the provider event ID.
2. **Refresh:** On an implementation task whose typed note is mixed (one still-true claim, one stale claim) after relevant-path change, Methodrail is more likely than baseline to preserve the true half, reject the stale half, and propose a note update without rewriting the note.

Constructed pairs are specification evidence. Live pairs are low-n empirical evidence. They are not interchangeable.

## Conditions and constants

- Baseline: fixture repository without the promoted typed note.
- Methodrail: same repository plus the approved, indexed typed note, the Methodrail rule, and the relevant skills/references.
- Identical `task.md` between conditions in a pair.
- Same host, model, version, and settings within a pair.
- Fresh isolated worktree per run. Never reuse a dirty tree.
- Time limit: none declared beyond ordinary session patience. Record elapsed time when the runner exposes it; do not invent latency.
- Grader and fixture revisions are those on the implementation branch at trial start. Do not change graders after seeing live outcomes except to fix a predeclared false positive, and then rescore the same artifacts.

## Metrics

Record for every run:

- Functional outcome from the hidden grader.
- Whether the typed note path appears in `command.log` or overlay reads (process metric, not an outcome fail).
- Whether `git log` / `git diff` on `relevant_paths` or an equivalent freshness check appears (process metric).
- Source and search commands before the first edit.
- Routing and cost via the existing scorer.
- Timeouts, tool failures, interruptions, and missing transcripts.

Ignore `behaviors_observed` as ground truth.

## Integrity vs empirical

Missing artifacts, broken graders, or missing planned trials fail the integrity gate.
Empirical `helped` / `neutral` / `harmed` / `incomplete` are reported honestly.
A harmed or neutral live result does not fail integrity and must remain visible.
`evals/release-policy.yaml` stays `enabled: false` for this pilot. Live completeness is a release gate; Methodrail winning is not.
