# v0.9.0 Project Artifact Interoperability Implementation Plan

Status: accepted implementation handoff (contract verified against v0.8.0 at `046342b`)

Prepared: 2026-09-01

Baseline: `046342b4cfa012dc33ca5527ef680900bd3e2161` (`v0.8.0`, `main`)

Product contract: [v0.9-project-artifact-interoperability.md](v0.9-project-artifact-interoperability.md)

## Executive decision

Ship v0.9.0 as **Project Artifact Interoperability**.

Do not create `setup-methodrail`. Improve `methodrail-init` into the single discover/preview/confirm/apply/verify owner. Keep project artifacts separate by authority, connect them through `.methodrail/PROJECT.md`, add explicit decision and verification/knowledge bridges, and strengthen architecture maintenance with evidence and verification handoffs.

The implementation sequence is:

```text
freeze contract and re-check upstreams
        ↓
methodrail-init inventory + preview/apply contract
        ↓
operational-decision → ADR promotion bridge
        ↓
knowledge health + reconciliation + verification links
        ↓
evidence-backed architecture maintenance
        ↓
constructed specifications
        ↓
mixed-repository dogfood
        ↓
predeclared live pilot
        ↓
release closure
```

Each vertical slice must be independently reviewable and green. Do not combine upstream refreshes, skill behavior changes, graders, and live artifacts in one commit.

## Definition of done

v0.9.0 is done only when all of the following are true:

- `methodrail-init` safely previews and applies a mixed-artifact project harness and immediately reruns as a no-op;
- existing project-native, pstack-shaped, Matt-shaped, and Superpowers-shaped artifacts remain canonical and unmodified unless an explicit Methodrail-owned block was approved;
- operational TSV decisions can lead to approved standalone ADRs without changing the pstack-compatible TSV schema;
- knowledge health identifies likely staleness and governance problems without presenting freshness as correctness;
- reconciliation can reuse project verification and cannot mutate durable knowledge without approval;
- feature maps can link canonical project knowledge without becoming a knowledge dump;
- `improve-codebase-architecture` distinguishes pass-through deletion, real deepening, and already-deep modules, and produces a verification-ready refactor brief;
- constructed graders are artifact-backed and adversarially calibrated;
- mixed-repository dogfood is recorded honestly;
- the predeclared live battery is complete and preserved;
- all existing v0.8 notes and historical evals remain valid and unchanged;
- version, README, changelog, and release claims match recorded evidence.

## Stage C — Implement the decision ladder

### C1. Align the decision contract

Primary files:

```text
references/protocols/decision-record.md
references/decision-frontier.md
references/skill-composition.md
templates/project/knowledge/decisions/decision.md
skills/show-me-your-work/SKILL.md
skills/domain-modeling/SKILL.md
skills/grill-with-docs/SKILL.md
skills/reflect/SKILL.md
```

Make the ADR gate canonical:

```text
hard to reverse
+ surprising without context
+ real trade-off
= offer an ADR
```

Treat consequential scope, public contracts, security, data migration, cross-domain reach, and repeated reopening as signals, not substitutes.

Keep the six-column TSV format byte-compatible. Do not add IDs, significance columns, `promoted_to`, or a resolver schema.

### C2. Define promotion and reversal

Promotion behavior:

1. Identify a material operational decision from the active run.
2. Recheck current evidence and ADR eligibility.
3. Draft a standalone ADR.
4. Wait for approval.
5. Write the ADR at the existing canonical location.
6. Append a normal TSV promotion row only when the log is retained.

The ADR must not depend on an ephemeral TSV row to be intelligible.

Reversal behavior:

- operational-only decision → append a reversing/superseding TSV row;
- active ADR → approved new ADR with explicit supersession;
- conflicting later TSV → cannot override the ADR.

### C3. Decision tests

Add cases for:

- reversible task-local choice remains TSV-only;
- consequential but obvious/no-tradeoff choice does not automatically become an ADR;
- all three ADR conditions produce an offer, not an unapproved file;
- approval produces a standalone ADR and optional promotion row;
- rejected proposal creates no ADR;
- TSV reversal is append-only;
- ADR supersession requires approval;
- spreadsheet-formula hardening in `log.sh` remains intact;
- existing pstack TSV input remains readable and unchanged.

Do not require every Methodrail task to create a decision log.

## Stage D — Strengthen knowledge maintenance

### D1. Strengthen existing note sections

Primary files:

```text

```

Add a focused maintenance reference if needed:


Do not change typed frontmatter. Clarify `## Evidence` and `## Refresh triggers`:

- Evidence identifies a repeatable revalidation route or an honest manual boundary.
- Evidence says what it proves and what it does not prove when ambiguity is material.
- Refresh triggers include relevant non-path assumptions in prose.
- Missing or broken revalidation evidence yields uncertainty, not automatic retirement.
- `validated_at` changes only after approved reconciliation.

Existing notes remain valid without migration. Do not make richer prose retroactively repository-invalid.

### D2. Define evidence-backed reconciliation

Update the shared reuse procedure instead of copying reconciliation steps into every workflow.

Required behavior:

```text
identify affected claim slice
→ check governance, applicability, and Git freshness
→ inspect only implicated current sources and decisions
→ reuse a linked verification feature or strongest available evidence
→ supported | narrowed | contradicted | superseded | uncertain
→ continue current work from current evidence
→ optionally hand one mutation to reflect
→ wait for approval
```

When a note contains both still-valid and stale material, preserve the valid portion in reasoning and propose a bounded correction. Do not trust the whole note, delete the whole note, or block source-grounded work.

### D3. Release-time knowledge audit

Document a synchronous release procedure:

- enumerate notes relevant to changed public behavior;
- include release-relevant `review-required` and `unknown` notes;
- run practical falsification routes for critical invariants;
- sample a small number of apparently fresh notes when risk justifies checking incomplete dependencies;
- record outcomes in the release/dogfood report, not a permanent knowledge-use ledger;
- route approved changes through `reflect` before the release evidence is frozen.

Do not introduce time-to-live fields or numeric confidence.

### D4. Knowledge-maintenance tests

Add cases for:

- unchanged relevant paths reported as dependency-fresh but not semantically proven;
- non-path trigger text leading to targeted inspection rather than automatic status change;
- linked test/verification evidence passes and supports only the stated boundary;
- linked evidence is missing or fails;
- partially stale note is narrowed rather than discarded;
- contradiction changes current task behavior but not the durable note without approval;
- `reflect` proposes at most one mutation;
- approval updates evidence and `validated_at` atomically;
- an unchanged rerun produces no diff;
- no queue, receipt, transcript, or lookup log is written.

### I3. Hypotheses

1. **Decision ladder:** Methodrail is more likely to keep reversible choices lightweight while withholding an ADR until a genuinely qualifying decision is approved.
2. **Knowledge reconciliation:** Methodrail is more likely to use current evidence, preserve the valid claim slice, and avoid unapproved knowledge mutation.
3. **Architecture deepening:** Methodrail is more likely to distinguish pass-through, shallow, and already-deep modules and to demand a credible behavior-preservation path before recommending work.

### I4. Metrics

- artifact-backed functional outcome;
- correct skill/routing ownership;
- current project knowledge inspected before recommendation;
- source/history/verification evidence used;
- unwanted durable artifact mutation;
- decision significance classification;
- note reconciliation disposition;
- architecture candidate classification;
- verification commands and evidence;
- source/search commands before first edit;
- tool failures, interruptions, timeouts, and missing artifacts;
- empirical pair verdict: `helped | neutral | harmed | incomplete`.

### I5. Predeclared release policy

Record policy in `evals/release-policy.yaml` before the first run:

- integrity completeness is mandatory;
- all constructed v0.9 specifications must pass;
- empirical winning is not mandatory;
- live harm caused by an unapproved ADR/knowledge mutation blocks release;
- live harm caused by trusting stale knowledge blocks release;
- live harm caused by editing source during an architecture survey blocks release;
- live harm caused by confidently recommending an already-deep or quiet speculative target blocks release pending investigation;
- neutral results are acceptable when Methodrail preserves safety without measurable outcome improvement;
- do not change thresholds after seeing results.

Never delete, replace, selectively rerun, or relabel an unfavorable valid trial. Grader corrections must be labeled and rescore preserved artifacts.

## Risk register

### Setup becomes a second runtime

Risk: preview/apply logic grows into a consumer orchestration engine.

Control: keep it as skill procedure plus existing deterministic helpers; no service, state machine, or installed project dependency.

### `PROJECT.md` becomes a universal manifest

Risk: every artifact and status is copied into one stale file.

Control: links and roles only; omit low-value sections; preserve size limits.

### Compatibility becomes format conquest

Risk: Methodrail rewrites upstream/project artifacts into its preferred layout.

Control: adopt by pointer; content hashes in dogfood; no migration in v0.9.

### Freshness creates false confidence

Risk: users read `fresh` as `true`.

Control: dependency-fresh wording, evidence boundaries, adversarial reconciliation fixtures, no automatic semantic pass.

### Reconciliation becomes a knowledge-writing bot

Risk: evidence automatically advances `validated_at` or rewrites claims.

Control: `reflect` remains the only approval bridge; guardrail overlays fail any unapproved mutation.

### Decision promotion creates ADR spam

Risk: every operational row becomes a durable record.

Control: all three ADR criteria required; proposals are bounded; no automatic promotion.

### Feature maps become duplicated specs

Risk: related knowledge is copied into verification files.

Control: links plus one-line relationships only; artifact-backed grader rejects copied claims.

### Architecture survey becomes speculative cleanup

Risk: polished reports legitimize quiet-code rewrites.

Control: churn/friction evidence, calibrated strengths, no source edits, verification-ready handoff.

### HTML adds failure surface

Risk: remote assets fail or unread output is presented.

Control: Markdown default, explicit fallback, render-and-inspect requirement.

### Milestone scope becomes too broad

Risk: init, decisions, knowledge, verification, and architecture land as one inseparable change.

Control: preserve the vertical slices and commit boundaries above; each slice must be green and separately reviewable; defer typed schemas and automation.
