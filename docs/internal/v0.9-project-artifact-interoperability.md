# v0.9 Project Artifact Interoperability

Status: accepted product contract for implementation on `feat/v0.9-project-artifact-interoperability`.

Baseline: v0.8.0 Knowledge Governance at `046342b4cfa012dc33ca5527ef680900bd3e2161`.

Methodrail remains methodology plus a project harness. Native agents perform project work. Repository TypeScript validates Methodrail contracts, fixtures, and recorded evals; it does not become a required consumer runtime.

## Release thesis

v0.8 made individual typed notes safer to reuse. v0.9 makes the surrounding project artifacts work as one navigable system without collapsing their different authority or freshness rules.

```text
existing project artifacts
        +
read-only repository discovery
        +
explicit authority and routing rules
        ↓
methodrail-init preview
        ↓ human confirmation for writes
.methodrail/PROJECT.md pointer index
        ↓
task-time decision, knowledge, and verification bridges
```

The v0.9 promise is:

> One initialization workflow, separate canonical artifacts, explicit governed bridges.

## Outcomes

1. `methodrail-init` is the only Methodrail setup and refresh owner.
2. Existing pstack-, Matt Pocock-, Superpowers-, and project-native artifacts remain canonical at their existing paths and are adopted by pointer, not copied or converted.
3. Operational TSV decisions and durable ADRs form a two-rung decision ladder.
4. Project knowledge, verification feature maps, verification procedures, and run evidence are cross-navigable without being treated as interchangeable.
5. Code-derived knowledge gets a read-only health report plus evidence-backed reconciliation; freshness is never presented as semantic correctness.
6. Architecture-maintenance recommendations are grounded in observed friction, current knowledge, and a credible behavior-preservation path.

## Constraints

- Keep Git-root `.methodrail/PROJECT.md` as the only Methodrail project discovery entry point.
- Support ordinary and repository-bound linked-external harnesses through the same canonical `.methodrail/` path.
- Do not add `setup-methodrail`; improve `methodrail-init` instead.
- Do not add another global router or activate `poteto-mode`, `ask-matt`, or `using-superpowers`.
- Do not move, normalize, or rewrite existing project-native artifacts merely to make them look Methodrail-native.
- Existing project instructions and canonical project documents outrank Methodrail assumptions.
- Preserve v0.8 typed-note schema, identity, eligibility, lifecycle, scope, and approval semantics.
- Do not add typed-note frontmatter fields in v0.9.
- Do not automatically create, revise, dispute, resolve, retire, replace, or revalidate durable knowledge.
- Do not automatically create or supersede an ADR.
- Do not treat a decision log, feature map, verification procedure, or historical run as proof of current behavior.
- Do not persist prompts, transcripts, source snippets, lookup receipts, candidate queues, confidence scores, or an automatically harvested knowledge inbox.
- Do not add a database, graph store, vector search, file watcher, daemon, scheduler, background reconciliation process, or consumer workflow runtime.
- Do not execute arbitrary commands discovered in knowledge prose during initialization.
- Keep simple projects and trivial tasks cheap.

## Artifact authority

Compatibility means preserving these distinctions.

| Artifact | Canonical question | Authority | Freshness / lifecycle | v0.9 bridge |
| --- | --- | --- | --- | --- |
| `.methodrail/PROJECT.md` | Where are the project sources an agent should open? | Methodrail-owned pointer index | Link and structure validation | Points to all relevant artifact roots without copying them |
| Project glossary / domain docs | What do project terms mean? | Project maintainers | Human-maintained; unknown unless checked | Indexed and reused by domain-aware skills |
| Specs and plans | What should be built, and how is work decomposed? | Their owning project workflow | Current only by project convention | Indexed as intent/planning artifacts, never promoted automatically |
| ADR / durable decision record | Which consequential choice governs, and why? | Project maintainers after approval | Active until explicitly superseded | May be promoted from an operational decision; remains standalone |
| Operational `decisions.tsv` | What did this run choose or observe at a decision point? | Producing run | Append-only historical trail | May record ADR promotion or reversal; never overrides an ADR |
| Typed Methodrail note | What scoped reusable claim may an agent rely on? | Approval-gated Methodrail knowledge workflow | v0.8 status, lifecycle, scope, and freshness | May point to project knowledge or verification; updated only through `reflect` |
| Verification feature map | Which user-facing behavior exists, and how can it be exercised? | Project-local verification skill | Maintained through source inspection and live exercise | May link related project knowledge; does not claim a current pass |
| Verification skill / control procedure | How do we launch, drive, inspect, reset, stop, and prove behavior now? | Project-local harness | Maintained by its native workflow | Reused by verification and reconciliation |
| Verification evidence | What happened in one run against one state? | Producing verification workflow | Immutable observation of that run | May support reconciliation; never mutates knowledge automatically |

No lower-authority artifact silently overrides a higher-authority one. In particular:

- current source and fresh behavioral evidence outrank a stale note for the active task;
- an active ADR outranks a conflicting operational TSV row;
- a feature map is a proof recipe, not a successful proof;
- historical evidence remains evidence of its captured run, not current state;
- a project document is not a typed Methodrail note merely because `PROJECT.md` links it.

## `methodrail-init` contract

`methodrail-init` remains explicit-only and serves both first-time setup and refresh. It owns one workflow:

```text
discover → classify → preview → confirm → apply → verify no-op
```

### Discovery

Inspect before asking the user. In addition to the existing repository interview, discover recognizable artifact roles:

- existing `.methodrail/` directory or validated linked harness;
- `AGENTS.md`, `CLAUDE.md`, Cursor rules/skills, Claude skills, `.agents/skills/`, `.codex/`, and Copilot instructions;
- canonical glossaries such as `CONTEXT.md`, `CONTEXT-MAP.md`, and established project equivalents;
- ADR and decision-record locations;
- project specs, plans, tickets, and scratch conventions;
- pstack-shaped `decisions.tsv`, `.audit/*.tsv`, verification skills, and `features/` maps;
- Matt-shaped domain docs and ADRs;
- Superpowers-shaped `docs/superpowers/specs/` and `docs/superpowers/plans/`;
- Methodrail typed and legacy knowledge;
- project control, runtime, test, and verification procedures.

Recognize an artifact by content and role, not filename alone. Ambiguous ownership or conflicting canonical candidates stays unresolved.

### Classification

Every proposed target is classified as one of:

- `create` — Methodrail-owned artifact is absent and justified;
- `update` — a Methodrail-owned block is stale;
- `adopt` — an existing canonical artifact should be indexed without content changes;
- `unchanged` — current state already satisfies the contract;
- `conflict` — ownership or canonical destination is ambiguous;
- `unavailable` — a valuable capability cannot be established from the current checkout or environment.

These labels are a user-facing planning contract, not a new stored manifest schema.

### Preview and confirmation

Before a non-empty write, show:

- exact files or owned blocks to create or update;
- existing artifacts to adopt by pointer;
- preserved files that will not be changed;
- conflicts and unavailable capabilities;
- whether the harness is in-repository or linked external storage;
- whether a project-local verification skill is present, justified, missing, or blocked.

Invocation authorizes inspection. A non-empty write plan requires explicit confirmation. A no-op refresh reports `unchanged` and performs no confirmation ceremony.

### Apply

- Write only the confirmed plan.
- Preserve native artifact formats and locations.
- Modify shared instruction files only inside unmistakable Methodrail-owned blocks.
- Do not create files under `.methodrail/knowledge/`.
- Do not run knowledge evidence recipes or mutate decision governance during init.
- Preserve the linked-harness binding and visibility choice.
- If state changed after preview, stop rather than applying a stale plan.

### Verify

After apply:

1. Re-run discovery.
2. Confirm links, paths, frontmatter, harness binding, and supported integration.
3. Confirm the applied state matches the approved preview.
4. Confirm an immediate unchanged refresh proposes no writes.

## `PROJECT.md` compatibility index

`PROJECT.md` remains small and pointer-oriented. Use existing semantic sections rather than creating a universal artifact registry. Depending on repository evidence it may point to:

- domain vocabulary;
- architecture and product specifications;
- active ADRs and their index;
- operational decision-log conventions;
- typed knowledge;
- verification skill and feature-map root;
- runtime/control guidance;
- existing AI instructions.

Each pointer should make the artifact role clear. Do not duplicate authority, freshness, or claim content in the index. Do not mark an adopted artifact as Methodrail-owned.

## Decision ladder

### Rung 1: operational decisions

Use the existing pstack-compatible six-column TSV format unchanged:

```text
ts	phase	decision	why	evidence	result
```

- Default location remains a working `decisions.tsv` or `.audit/<task>.tsv`.
- Default persistence remains local/ephemeral; commit only when reviewability justifies it.
- Append one row per material fork, pivot, revert, or verified checkpoint.
- Reverse a small decision by appending a later row; never edit history.
- No stable ID column, resolver service, or new TSV schema is added in v0.9.

### Rung 2: durable ADRs

Offer an ADR only when all three are true:

1. the choice is meaningfully hard to reverse;
2. it would be surprising without its rationale;
3. it resolves a real trade-off among credible alternatives.

Consequential scope, public contracts, data migration, security, cross-domain reach, or repeated reopening are strong signals, but do not replace the three-part test.

Promotion requires explicit approval:

1. Reconstruct the decision and current evidence.
2. Draft a standalone ADR in the project's canonical decision location.
3. Wait for approval.
4. Write the approved ADR.
5. If the operational log remains available, append a normal TSV row recording promotion and use the ADR path as evidence.

The ADR must stand alone if the working TSV is later discarded. A TSV reversal cannot override an active ADR; changing it requires an approved superseding ADR.

## Knowledge maintenance and reconciliation

### Preserve the v0.8 schema

`kind`, `status`, `validated_at`, `relevant_paths`, lifecycle, scope, disputes, and retirement retain their v0.8 meaning. v0.9 strengthens the required Markdown sections rather than adding frontmatter.

### Evidence section

For a high-value code- or behavior-derived claim, `## Evidence` should identify the strongest practical revalidation route:

- a deterministic test or command;
- a project verification feature;
- a source, schema, specification, or active ADR pointer;
- a bounded manual inspection when execution is impossible.

State what the evidence establishes and, when ambiguity is likely, what it does not establish. Do not embed executable command fields that init will run automatically.

### Refresh triggers section

`## Refresh triggers` should name material non-path invalidators when they exist, such as:

- dependency or external API changes;
- configuration or schema changes;
- a superseding ADR or specification;
- project control or deployment changes;
- failure of a linked verification feature;
- a change in the boundary or assumption named by the claim.

`relevant_paths` remains the only deterministic source-change freshness input in v0.9. Other triggers guide targeted reconciliation. Missing or unevaluable evidence reduces confidence; it never produces a false `fresh` claim.

### Read-only health report

Every `methodrail-init` refresh reports indexed knowledge as applicable:

- valid and dependency-fresh;
- `review-required`;
- `unknown`;
- malformed;
- disputed;
- retired;
- unbounded;
- broken or missing from the PROJECT index;
- carrying broken evidence or verification pointers that can be checked safely.

The report says explicitly that `fresh` means no declared relevant path changed since validation, not that the claim is semantically true.

### Reconcile on use

When a task materially relies on partial, provisional, stale, unknown, or contradicted knowledge:

1. Identify the affected claim slice and task-relevant paths.
2. Run cheap Git freshness and governance checks.
3. Inspect only implicated source, decisions, configuration, tests, and verification features.
4. Run the strongest relevant evidence route when practical.
5. Classify the material claim as supported, narrowed, contradicted, superseded, or uncertain.
6. Continue the active task from current source and fresh evidence.
7. If durable knowledge should change, invoke `reflect` with at most one proposed governance mutation.
8. Wait for explicit approval before changing the note or advancing `validated_at`.

Do not create a reconciliation queue, receipt database, or permanent reuse log.

### Release-time audit

Before a significant release, reconcile:

- notes connected to changed public behavior;
- `review-required` or `unknown` notes that could affect the release;
- release-critical invariants with a practical falsification route;
- a small adversarial sample of apparently fresh notes when the release risk justifies checking for incomplete `relevant_paths`.

This is synchronous release work, not scheduled background maintenance.

## Verification and knowledge bridge

The canonical relationship remains:

```text
project knowledge: what should hold, and why
verification feature: how a user-visible behavior can be exercised
verification evidence: what happened in this run
reflect: whether evidence earns a durable knowledge mutation
```

### Feature-map extension

A feature file may add an optional `## Related project knowledge` section after `## Sub-features`. It contains only relevant links to canonical glossary entries, specs, ADRs, or typed notes, with one-line relationship descriptions.

- Do not require this section when no relationship adds value.
- Do not copy claims into the feature map.
- Do not treat a linked note as current without its native eligibility check.
- Do not add implementation-path inventories to user-facing feature files.

### Creation and maintenance behavior

- `create-verification-skill` may use canonical docs and eligible knowledge to discover intended features, but must confirm the user path from current source and live behavior.
- `maintain-verification-skill` reads related project knowledge during source reconciliation.
- A wrong feature description is verification-map drift.
- A working feature the harness cannot drive is a harness gap.
- Broken product behavior is a product gap.
- A contradiction with project knowledge is a reconciliation finding.
- Verification maintenance may update its own files; it never rewrites ADRs or typed knowledge.
- Fresh verification evidence may feed `reflect`; it never crosses the durable knowledge boundary automatically.

## Architecture-maintenance contract

`improve-codebase-architecture` remains an explicit survey/decision operator. `/refactor` owns behavior-preserving implementation.

### Correct candidate test

Separate two questions:

1. **Existence:** if the module is deleted, does complexity vanish or reappear across callers?
2. **Depth:** if the module earns its existence, is its interface still too wide, leaky, or difficult to test?

A pass-through is a deletion/consolidation candidate. A module that earns a seam but exposes too much is a deepening candidate. An already-deep module is not a candidate merely because deleting it would hurt callers.

### Evidence-backed candidates

Every candidate names:

- observed friction and its evidence;
- relevant churn, recurring defects, review cost, or current work;
- interface burden and leakage;
- affected callers and blast radius;
- related glossary, ADR, typed knowledge, and verification features;
- the behavior-preservation baseline or a concrete verification gap;
- expected locality/leverage gain;
- recommendation strength with a stated reason.

Recommendation meanings:

- `Strong` — demonstrated recurring friction, a credible smaller interface, and an honest verification path;
- `Worth exploring` — real friction, but the seam or verification path remains uncertain;
- `Speculative` — plausible improvement without enough usage, churn, or evidence to justify implementation.

### Presentation and handoff

- Markdown/in-conversation presentation is the default.
- Generate HTML only when a visual materially improves comparison.
- Generated HTML must be viewable without silently depending on unavailable CDNs, and the agent must inspect the rendered result before presenting it.
- After the user selects and grills a candidate, produce a compact refactor brief: friction, current/proposed interface, affected callers, behavior to preserve, baseline verification, blast radius, knowledge/ADR constraints, and unresolved decisions.
- Behavior-preserving work returns to `/refactor`.
- Intentional behavior change routes to `/develop`.
- Large independently landable work may route to `to-spec` / `to-tickets`.
- An operational selection may be logged in TSV; only a qualifying approved choice becomes an ADR.

## Upstream compatibility

Methodrail remains a curated family organized by capability, not upstream brand.

### pstack

- Preserve six-column decision-log compatibility.
- Recognize project-local verification skills and feature maps.
- Reuse adopted understanding, architecture, parallel, verification, forensics, and reflection operators through their Methodrail owners.
- Do not import `poteto-mode`, setup model-role configuration, or the `principle-*` library as a second operating system.

### Matt Pocock skills

- Recognize project glossary/domain layouts, ADRs, specs, and plans.
- Preserve the ADR significance threshold and deep-module vocabulary through Methodrail owners.
- Do not import `ask-matt` or `implement` as a competing lifecycle.

### obra/superpowers

- Preserve the hard evidence gate behind `verify-change`.
- Preserve selected debugging and TDD pressure-resistance behavior through `diagnosing-bugs` and `tdd`.
- Recognize existing Superpowers specs and plans as project-native intent/planning artifacts.
- Do not import `using-superpowers`, its planning/execution chain, review handshake, or parallel execution control plane.

Mixed installations must not create recursive workflows or require duplicate completion gates.

## Deferred beyond v0.9

- new typed-note dependency or evidence frontmatter;
- automatic evaluation of arbitrary non-path refresh triggers;
- semantic contradiction detection;
- claim IDs or claim-level storage;
- stable operational-decision IDs or a decision resolver;
- automatic ADR promotion;
- persistent verification receipts or reuse logs;
- wall-clock knowledge expiration or numeric confidence;
- scheduled/background audits;
- universal artifact manifests, knowledge graphs, or event journals;
- automatic migration of upstream-shaped artifacts;
- a new setup skill, global router, or consumer workflow runtime.

## Product acceptance

v0.9 is acceptable when:

- one `methodrail-init` run can safely discover, preview, connect, and refresh a mixed-artifact repository;
- the preview is exact, confirmed writes are bounded, and an unchanged second run is a no-op;
- existing pstack-, Matt-, Superpowers-, and project-native artifacts remain byte-identical unless they contain an explicitly owned Methodrail block;
- operational decisions can be promoted to standalone ADRs without changing TSV format or bypassing approval;
- knowledge health reports likely staleness without claiming semantic truth;
- reconciliation reuses current evidence and cannot silently mutate durable knowledge;
- verification feature maps can point to canonical project knowledge while retaining separate authority;
- architecture recommendations reject pass-through/deep-module confusion and include a credible verification handoff;
- existing v0.8 notes remain valid without migration;
- historical evals and live reports remain unchanged;
- no second control plane, automatic knowledge store, or consumer runtime appears.
