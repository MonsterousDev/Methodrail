# v0.8 Knowledge Governance

Internal product contract. Freeze disagreements here before changing parsers or fixtures.

Baseline: v0.7.1 linked-external harness (`release/v0.7.1-linked-harness`). Released as 0.8.0. The live C7 battery remains declared, not executed.

Methodrail remains methodology plus a project harness. Native agents do the work. Repository TypeScript validates contracts, fixtures, and evals. It is not a consumer runtime.

## Vertical slice

```text
task-relevant paths
        +
typed note scope, lifecycle, status, and freshness
        ↓
deterministic eligibility decision
        ↓
eligible | reconcile-required | not-applicable | blocked
        ↓
agent uses, narrows, reconciles, or refuses the note
```

The next unknown after v0.7 is not whether another note can be stored. It is whether an agent can tell when a true note applies only to part of a repository, when it conflicts with another claim, and when it must no longer be used.

## Constraints

- Keep `.methodrail/PROJECT.md` at the Git root as the only discovery entry point.
- Support in-repository `.methodrail/` and repository-bound linked-external storage identically for parsing and validation.
- TypeScript stays a maintainer/eval implementation, not a required consumer runtime.
- Explicit human approval before creating, modifying, disputing, resolving, retiring, or replacing durable knowledge.
- Typed-note identity is the file path. Do not move a note to represent retirement.
- Legacy notes remain loadable with reduced confidence.
- Do not silently migrate existing typed notes. Omitted `lifecycle` means `active`. Omitted `scope` means `unbounded`.
- Do not persist prompts, transcripts, source snippets, or a lookup log.
- Do not add embeddings, vector search, a database, a file watcher, a daemon, agent leases, or a candidate queue.
- v0.8 scope is repository-path-only. No runtime, environment, or deployment scope.
- Conflict creation is explicit and human-reviewed. Do not auto-detect semantic contradictions.
- Do not rewrite T6, T8, T9, historical pilots, or historical reports.
- Constructed specifications and live empirical results stay separately labeled.
- Eligibility proves whether a note may be used for named task paths. It is not a reuse receipt.

## Typed-note schema

Required v0.7 fields remain: `kind`, `status`, `validated_at`, `relevant_paths`. Optional governance fields:

```yaml
lifecycle: active
scope:
  include_paths:
    - src/notifications
  exclude_paths:
    - src/notifications/legacy
```

Lifecycle-specific fields appear only when needed:

```yaml
lifecycle: disputed
conflicts_with:
  - knowledge/other-claim.md
```

```yaml
lifecycle: retired
superseded_by: knowledge/current-claim.md
```

Rules:

- `lifecycle` is `active | disputed | retired`. Omitted means `active`.
- `scope` is optional. Omitted means `unbounded`, not invalid.
- `include_paths` and `exclude_paths` are optional. When present they are non-empty arrays.
- Scope entries are repository-relative file or directory prefixes, slash-canonical, not globs. Reject `*`, `?`, bracket patterns, NULs, absolute paths, repository-root-only paths, and traversal.
- Matching is exact-path or descendant matching on a path-segment boundary. `src/mail` matches `src/mail/send.ts`, not `src/mailer.ts`.
- Exclusion wins over inclusion.
- Omitted `include_paths` means all repository paths are candidates except exclusions.
- `conflicts_with` is allowed only when lifecycle is `disputed`. Identities are `.methodrail`-relative (`knowledge/<slug>.md`). References must exist, target typed notes, not be self, and be reciprocal.
- `superseded_by` is allowed only when lifecycle is `retired` and targets one existing non-retired typed note in the same identity form. Cycles are invalid.
- A retired note without `superseded_by` must have a meaningful `## Retirement` section.
- A disputed note must have a meaningful `## Dispute` section.
- Claim, Evidence, Reuse guidance, Refresh triggers, size, provenance, hypothesis, and indexing rules remain in force.
- Decisions stay decision records. Do not apply this lifecycle contract to ADRs in this slice.
- A note that contains only a governance field, without the v0.7 required fields, is `invalid-typed`, not legacy. Malformed `lifecycle` or `scope` is also `invalid-typed`. Eligibility is `unknown` whenever `governanceErrors` is present; do not default a bad field to `active` or unbounded and then treat the note as eligible.

Do not add runtime names, deployment modes, environment names, arbitrary predicates, or a scope expression language.

## Scope evaluation

A pure evaluator receives a parsed note and explicit task-relevant paths. It does not inspect prompts or infer intent.

```text
unbounded | applicable | partial | not-applicable | unknown
```

- No explicit task paths → `unknown`.
- No scope block with task paths → `unbounded`.
- Every task path is included and none excluded → `applicable`.
- At least one applies and at least one is excluded or outside includes → `partial`.
- None apply because every path is excluded or outside includes → `not-applicable`.
- Evidence arrays are normalized and sorted so reruns are byte-stable.
- Invalid task paths are rejected at the boundary; do not normalize traversal into the repository.

Task-relevant paths are the paths to which the claim might be applied, not every file the task touches. Tests may be part of an implementation without automatically making a source-scoped note partial.

## Eligibility

A pure composition of classification, status, lifecycle, freshness, and scope. Decision order:

1. Governance errors → `unknown`
2. Retired → `blocked-retired`
3. Disputed → `blocked-disputed`
4. Legacy or invalid typed note → `unknown`
5. Scope `not-applicable` → `not-applicable`
6. Provisional status → `reconcile-required`
7. Scope `partial` or `unknown` → `reconcile-required`
8. Freshness `review-required` or `unknown` → `reconcile-required`
9. Verified + fresh + scope applicable or unbounded → `eligible`

`evaluateProjectKnowledge()` stays repository-wide and task-agnostic. Task-aware eligibility is a separate function. Do not write eligibility artifacts into `.methodrail`.

Disputed and retired notes are not repository-invalid. They cannot be eligible.

## Agent behavior

Update the shared reuse procedure so agents:

1. Identify only the task paths relevant to a candidate note's claim.
2. Read lifecycle before applying the claim.
3. Refuse retired knowledge.
4. Present disputed claims and current evidence without selecting a winner.
5. Apply an eligible scoped note only inside its applicable paths.
6. Reconcile partial, provisional, stale, or unknown knowledge against current source.
7. Name the disposition and note path when a note materially affects the task.
8. Propose at most one governance mutation and wait for explicit approval.

A reciprocal dispute may update both notes and the PROJECT.md pointer set as one approved transaction.

Trivial work and unrelated notes do not need a knowledge decision ceremony.

## Deferred beyond v0.8

Automatic semantic contradiction detection; runtime/environment/symbol scope; wall-clock expiration; cryptographic receipts; agent leases; automatic migrations; transcript harvesting; cross-repository discovery; embeddings; background cleanup.
