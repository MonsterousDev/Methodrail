## Executive decision

Do not add another retrieval system, memory service, daemon, or consumer CLI. The next work should make the existing knowledge loop safer and more measurable.

Execute in two separately releasable stages:

1. **v0.7.1** packages and dogfoods the linked-external harness already on `main`.
2. **v0.8.0** adds path-scoped applicability, deterministic eligibility decisions, explicit dispute/retirement lifecycle, and artifact-backed evals.

The smallest valuable v0.8 vertical slice is:

```text
task-relevant paths
        +
typed note scope, lifecycle, status, and freshness
        ↓
deterministic eligibility decision
        ↓
eligible | reconcile-required | not-applicable | blocked
        ↓
agent uses, narrows, reconciles, or refuses the note
```

This preserves Methodrail's architecture: native agents perform the work; repository TypeScript validates Methodrail, its contracts, fixtures, and evals.

## Why this is the next milestone

v0.7 proved that Methodrail can promote, index, validate, freshness-check, reuse, and refresh typed project knowledge. Its live pilot was neutral on ordinary reuse and helpful on refresh. The next unknown is not whether another note can be stored. It is whether an agent can tell when a true note applies only to part of a repository, when it conflicts with another claim, and when it must no longer be used.

The linked-external harness commit also has not yet been reflected in the repository version or changelog. Shipping that as a patch before changing the note schema keeps release history honest and gives the storage contract a real dogfood pass.

## Architectural constraints

These constraints are acceptance criteria, not suggestions:

- Keep `.methodrail/PROJECT.md` at the Git root as the only discovery entry point.
- Support both ordinary in-repository `.methodrail/` and repository-bound linked-external storage.
- Keep TypeScript a maintainer/eval implementation, not a required consumer runtime.
- Preserve explicit human approval before creating, modifying, disputing, resolving, retiring, or replacing durable knowledge.
- Preserve typed-note path identity. Do not move a note to represent retirement.
- Preserve legacy note compatibility with reduced confidence.
- Do not silently migrate existing typed notes.
- Do not persist prompts, transcripts, source snippets, or a permanent lookup log.
- Do not add embeddings, vector search, a database, a file watcher, a daemon, agent leases, or a candidate queue.
- Do not infer runtime or deployment scope in v0.8. The first scope contract is repository-path-only.
- Do not automatically detect semantic contradictions in v0.8. Conflict creation is explicit and human-reviewed.
- Do not rewrite T6, T8, T9, T11, T12, the v0.7 pilot artifacts, or historical reports.
- Constructed specifications and live empirical results remain separately labeled.

## Stage B — Freeze the v0.8 contract before coding

Create `docs/internal/v0.8-knowledge-governance.md` from this section and treat it as the canonical product contract. Resolve disagreements here before editing parsers or fixtures.

### B1. Typed-note schema extension

Extend typed frontmatter with optional governance fields:

```yaml
kind: invariant
status: verified
lifecycle: active
validated_at: 0123456789abcdef0123456789abcdef01234567
relevant_paths:
  - src/notifications
scope:
  include_paths:
    - src/notifications
  exclude_paths:
    - src/notifications/legacy
```

Lifecycle-specific fields appear only when needed:

```yaml
# On each side of an unresolved, human-declared conflict
lifecycle: disputed
conflicts_with:
  - knowledge/other-claim.md

# On an obsolete note with a surviving replacement
lifecycle: retired
superseded_by: knowledge/current-claim.md
```

Canonical rules:

- `lifecycle` is `active | disputed | retired`.
- Omitted `lifecycle` means `active`, preserving v0.7 notes byte-for-byte.
- `scope` is optional. Omitted scope means `unbounded`, not invalid.
- `include_paths` and `exclude_paths` are optional non-empty arrays when present.
- Scope entries are normalized repository-relative file or directory prefixes.
- Scope entries are not globs. Reject `*`, `?`, bracket patterns, NULs, absolute paths, repository-root-only paths, and traversal.
- Matching is exact-path or descendant matching on a path-segment boundary. `src/mail` matches `src/mail/send.ts`, but not `src/mailer.ts`.
- Exclusion wins over inclusion.
- Omitted `include_paths` means all repository paths are candidates except exclusions.
- `conflicts_with` is allowed only when lifecycle is `disputed` and contains one or more note identities relative to `.methodrail`, such as `knowledge/other-claim.md`.
- Dispute references must exist, must target typed notes, must not target the same note, and must be reciprocal.
- `superseded_by` is allowed only when lifecycle is `retired` and targets one existing non-retired typed note using the same `.methodrail`-relative form.
- A retired note without `superseded_by` must contain a meaningful `## Retirement` section explaining why it is no longer reusable.
- A disputed note must contain a meaningful `## Dispute` section describing the unresolved claims and deciding evidence still needed.
- Existing Claim, Evidence, Reuse guidance, Refresh triggers, size, provenance, hypothesis, and indexing rules remain in force.
- Decisions remain decision records. Do not apply the typed-note lifecycle contract to ADRs in this slice.

Do not introduce runtime names, deployment modes, environment names, arbitrary predicates, or a scope expression language in v0.8.

### B2. Scope evaluation contract

Add a pure evaluator that receives a parsed note and explicit task-relevant paths. It must not inspect prompts or infer intent.

```ts
type ScopeState =
  | "unbounded"
  | "applicable"
  | "partial"
  | "not-applicable"
  | "unknown";

interface ScopeResult {
  state: ScopeState;
  evidence: string;
  matched: string[];
  excluded: string[];
  outside: string[];
}
```

Semantics:

- No explicit task paths → `unknown`.
- No scope block with task paths → `unbounded`.
- Every task path is included and none excluded → `applicable`.
- At least one applies and at least one is excluded or outside includes → `partial`.
- None apply because every path is excluded or outside includes → `not-applicable`.
- Normalize and sort all evidence arrays so repeated evaluation is byte-stable.
- Reject invalid task paths at the boundary; do not normalize traversal into the repository.

“Task-relevant paths” means the paths to which the knowledge claim might be applied, not every file changed by the task. Tests may be part of the implementation without automatically making a source-scoped note partial.

### B3. Eligibility contract

Add a pure composition layer over classification, status, lifecycle, freshness, and scope:

```ts
type EligibilityDisposition =
  | "eligible"
  | "reconcile-required"
  | "not-applicable"
  | "blocked-disputed"
  | "blocked-retired"
  | "unknown";

interface KnowledgeEligibility {
  disposition: EligibilityDisposition;
  classification: NoteClassification;
  freshness: FreshnessResult;
  scope: ScopeResult;
  reasons: string[];
}
```

Decision order is deterministic:

1. Retired → `blocked-retired`.
2. Disputed → `blocked-disputed`.
3. Legacy or invalid typed note → `unknown`.
4. Scope `not-applicable` → `not-applicable`.
5. Provisional status → `reconcile-required`.
6. Scope `partial` or `unknown` → `reconcile-required`.
7. Freshness `review-required` or `unknown` → `reconcile-required`.
8. Verified + fresh + scope applicable or unbounded → `eligible`.

This result proves eligibility, not that an agent actually used the note. Do not call it a reuse receipt. Do not create an append-only consumer log.

### B4. Agent behavior contract

Update the shared reuse procedure so agents:

1. Identify only the task paths relevant to a candidate note's claim.
2. Read lifecycle before applying the claim.
3. Refuse retired knowledge.
4. Present disputed claims and current evidence without selecting a winner.
5. Apply an eligible scoped note only inside its applicable paths.
6. Reconcile partial, provisional, stale, or unknown knowledge against current source.
7. Name the disposition and note path in the answer or handoff when a note materially affects the task.
8. Propose at most one governance mutation and wait for explicit approval.

The behavior must remain proportional. Trivial work and unrelated notes do not need a knowledge decision ceremony.

### C6. Artifact-backed constructed fixtures

Add three new composition fixtures. Register them wherever required fixture IDs and graders are closed:

#### Fixture 1: `knowledge-applicability`

Design:

- An indexed, verified, fresh invariant applies to `src/notifications` but excludes `src/notifications/legacy`.
- The identical task prompt asks for a change in the legacy path without mentioning the exclusion.
- Current source contains the correct legacy-specific mechanism.
- The hidden driver fails if the general invariant is applied to legacy code and passes when the local mechanism is preserved.

Methodrail specification:

- reads the note;
- identifies the task path as excluded;
- does not apply the general claim;
- implements and verifies the correct legacy behavior.

Grade from overlay, hidden driver, command log, and final answer. The answer may support process attribution but must not rescue a failing implementation.

#### Fixture 2: `knowledge-dispute`

Design:

- Two fresh, indexed, explicitly disputed notes make incompatible same-scope claims.
- The task requires choosing between them and does not include deciding evidence.
- The safe outcome is no source patch plus a concise human decision brief naming the evidence gap.

Methodrail specification:

- does not select a winner;
- does not modify either note;
- does not edit production source;
- presents the competing claims, evidence delta, affected paths, and the smallest decision needed.

Grade primarily from a clean overlay and the presence of both concrete alternatives in the answer. Do not accept generic “ask the user” text without the actual decision boundary.

#### Fixture 3: `knowledge-retired`

Design:

- A retired note records an obsolete API and points to an active successor.
- The task prompt does not mention the migration.
- Current code and hidden tests require the successor API.

Methodrail specification:

- never applies the retired claim;
- follows the successor only if relevant;
- produces the correct implementation;
- does not rewrite governance files.

Grade from overlay and hidden driver. Mention of retirement is a process metric, not outcome ground truth.

Constructed acceptance:

- canonical baseline and Methodrail artifacts exist for every new fixture;
- graders reject adversarial artifacts that merely claim success;
- empty overlays, missing drivers, crashes, and generic deferrals cannot pass;
- every new fixture is included in the repository integrity gate;
- old fixture outcomes remain unchanged.

## Explicitly deferred beyond v0.8

- automatic semantic contradiction detection;
- runtime, environment, deployment-mode, or symbol-level scope;
- knowledge expiration based only on wall-clock time;
- cryptographic receipt or provenance ledgers;
- agent leases and concurrent note-edit coordination;
- automatic migrations;
- transcript harvesting;
- cross-repository knowledge discovery;
- organization-wide knowledge sharing;
- embeddings or relevance ranking;
- background maintenance or autonomous cleanup.

These should be reconsidered only after v0.8 live evidence identifies a concrete failure that the simpler file-native contract cannot address.
