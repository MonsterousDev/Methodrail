# Methodrail v0.6 audit

Internal maintainer record. Not a public architecture document.

Inspected 2026-08-24 against this repository and current upstream trees:

- [cursor/plugins pstack `how`](https://github.com/cursor/plugins/tree/main/pstack/skills/how)
- [mattpocock/skills](https://github.com/mattpocock/skills)
- [obra/superpowers](https://github.com/obra/superpowers)

Do not treat older snapshots as source.

## Current strengths

v0.5 already has a real family, not a bundle:

- One skill substrate, one composition model, one context-economics model.
- Workflow owners (`investigate`, `develop`, `debug`, `refactor`, `review`) stay orchestration boundaries. Leaves do not restart those lifecycles.
- Progressive disclosure is mostly honest: short skills, linked references, small global Cursor rule.
- Provenance is recorded (`UPSTREAM.md`, `upstreams/`, `THIRD_PARTY_NOTICES.md`).
- Project harness exists as `.methodrail/PROJECT.md` plus optional knowledge, control, and a project-local verify skill.
- Maintainer evals exist for routing, behavior, pressure, and complexity. They are specification-grade, not executable comparison.
- `verify-change` still carries Superpowers' iron law: no completion claim without fresh evidence.
- `how` already has explain/critique modes and links the four pstack prompt files. Host-specific model slugs were correctly removed.

## Fidelity gaps

### `how` (highest priority)

Classified `upstream-preserved-with-extensions`. The label is close, but the public skill under-exposes pstack behavior.

Current pstack `how` still has:

1. Explain by default; critique only when architecture is in question.
2. Simple vs complex split; lean simple.
3. Parallel read-only explorers for complex questions, then a separate explainer.
4. Explorer obligations: entrypoint, call/data flow, abstractions, boundaries, non-obvious facts, honest gaps.
5. Structured explorer output (components, flow, files read, boundaries, non-obvious, open questions).
6. Explainer communication style, including diagrams when they clarify.
7. Critique: explain first, independent critics, rubric, lead judgment (act / consider / noted / dismissed).

Methodrail keeps the skeleton and the four reference files. Gaps:

- `SKILL.md` summarizes exploration instead of requiring entrypoint, state, data/control flow, and boundaries as first-class work.
- Structured explorer output lives only in `explorer-prompt.md`. An agent that follows the public skill can skip it.
- Critique triggers are too narrow ("user asked for problems"). Missing: questionable structure, architectural constraints, "is this design good?", redesign evaluation. Critique is still correctly not the default.
- Critique flow names independent critics and lead judgment, but not architecture concerns and tradeoffs as explicit steps.
- Explainer mermaid/diagram guidance is not visible in the public skill.
- Methodrail extensions worth keeping: project-knowledge lookup, freshness, host-optional subagents, unknowns, evidence labels.

After restore, `upstream-preserved-with-extensions` remains the honest label.

### `verify-change`

Classified `methodrail-composed` (Superpowers gate + Methodrail evidence variety). Correct label.

The iron law is intact. Project-harness reuse is a one-liner. Missing a hard gate:

```text
before inventing verification
    → project verify skill?
    → control documentation?
    → runtime guidance?
    → existing test workflow?
    → if yes, reuse; do not rediscover
```

Do not weaken "no completion claim without fresh evidence."

### Other fidelity-priority skills

Inspected current Methodrail copies of `diagnosing-bugs`, `tdd`, `code-review`, `writing-for-agents`, `handoff`, `create-verification-skill`.

They still carry upstream procedure. Family wiring (project knowledge, neighbors, host degradation) is additive. No false `upstream-preserved` claims found on those files. Keep them stable; add fidelity evals rather than rewrites.

## Integration gaps

Every skill is supposed to inherit:

```text
project knowledge
verification capability
evidence semantics
freshness
context economics
proportional rigor
learning model
```

Today that contract is split across `references/methodrail-skill-substrate.md`, `references/project-harness.md`, and `rules/methodrail.mdc`. Cursor gets a small always-on rule. Claude and Codex adapters are shorter restatements, not projections of one source.

Consequences:

- Hosts can drift.
- Skills that invent verification (`verify-change`, `observe`, `tdd`, `diagnosing-bugs`) do not all check the same project surfaces first.
- `methodrail-init` aims at a pointer index, but quality is checklist prose, not a check.

`task packet` and `review packet` are current protocol names. Keep them. Obsolete v0.1 runtime language (`control adapter`, `result packet`, `runtime adapter`) is not in active skills; ban it so it cannot return.

## Evaluation gaps

`evals/` is a spec library:

- routing, behavioral, pressure, complexity YAML
- family-integration fixtures under `evals/fixtures/`
- validation of shape, ids, and coverage
- no runner, no recorded-run schema, no baseline-vs-Methodrail comparison, no report

That cannot answer "does Methodrail actually improve engineering behavior?" Maintainers can only read YAML and imagine agents.

Missing categories as executable suites:

- composition (skills reinforce each other)
- fidelity (upstream behavior not weakened)
- complexity cost (simple work stays cheap; hard work may cost more if it prevents expensive mistakes)

Do not add an agent runtime. Add a maintainer harness that scores recorded runs and golden examples.

## Unnecessary complexity

v0.5 already rejected a workflow engine, skill scheduler, and token optimizer. Keep that.

Remaining cost:

- Claude/Codex adapter text is a second copy of the Cursor rule.
- Eval corpus is large but not comparable.
- Some skills restate family methodology that now belongs in one invariant.
- Neighbor metadata (`Usually follows` / `Often produces` / `Escalate to` / `Avoid combining`) is absent, so composition is implied rather than named.

Do not add skills. Do not add control planes. Make the existing family measurable.

## Recommended changes

1. Restore public `how` procedure; keep host-optional subagents and evidence labels.
2. Add a project-verification reuse gate to `verify-change` without touching the iron law.
3. Extract `references/methodrail-family-invariant.md` and project it to Cursor, Claude, and Codex.
4. Add `evals/runners/`, composition/fidelity fixtures, complexity regressions, and comparison reports.
5. Tighten `methodrail-init` PROJECT.md quality (index, pointers, no README clone).
6. Extend `reflect` failure classification: knowledge / skill / verification / tooling / structural enforcement. Prefer enforcement over new prose.
7. Add neighbor metadata only where composition is non-obvious.
8. Dogfood a pointer-oriented `.methodrail/PROJECT.md` in this repository.
9. Ship as 0.6.0 Demonstrated Composition.

## Honest non-goals

Not in v0.6:

- new workflow engine or skill scheduler
- token optimizer
- another memory system
- public architecture redesign
- claiming live LLM benchmark scores in CI
- three independent host philosophies
